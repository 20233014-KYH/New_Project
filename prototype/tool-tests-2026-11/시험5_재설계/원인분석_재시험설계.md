# 왜 오픈소스가 "쓸 이유 없음"으로 나왔나 + 다시 시험하는 방법 (2026-11-13)

## 1. 한 줄 결론
**도구가 약한 게 아니라, 우리가 도구가 쓰이는 상황이 아닌 곳에서 시험했다.**
- 시험 과제가 작고 한 번에 끝나는 일이라, 기본 Claude가 이미 만점을 냈다(천장 효과).
- 오픈소스는 "기본 Claude가 모르는 절차", "긴 작업", "자동화", "실제 실행이 필요한 일"에서 차이가 난다.

## 2. 근거 (다른 사람들의 실제 사용·연구)
| 출처 | 내용 | 우리 시험과의 관계 |
|---|---|---|
| SkillsBench (arXiv 2602.12670, 84과제·7,308회) | 스킬은 평균 +16pp. 그런데 **소프트웨어 개발 분야는 +4.5pp로 가장 작음**. 모델이 원래 잘 아는 분야는 이득이 작고, 낯선 절차가 필요한 분야에서 크게 오름 | 우리는 Claude가 원래 잘하는 일(작은 버그·보안 구멍 찾기)만 냄 |
| ksred.com 스킬 비교 | 스킬이 맡는 과제에선 89% vs 기본 56%, **맡지 않는 과제에선 오히려 기본보다 못한 경우도 있음** | 도구가 맡는 상황을 정확히 골라야 함 |
| trailofbits variant-analysis 설명서 | 쓰는 때: **버그 하나를 찾은 뒤 "비슷한 게 또 있나"**, Semgrep·CodeQL 규칙 만들기. **쓰지 말 때: 처음 버그 찾기** (그땐 audit-context-building). semgrep·codeql 설치 필요. "이름으로 불러야 더 잘 쓴다" | 우리는 "처음 찾기"를 시켰음 = 설명서가 쓰지 말라는 상황 |
| claude-code-security-review 설명서·사용 후기(Deriv 등) | 핵심은 **GitHub Action: 모든 PR에 자동으로 돌고 줄에 댓글**, 팀 규칙·헛경보 제외 규칙을 고칠 수 있음 | 우리는 로컬 명령만 시험 → 기본 `/security-review`와 같은 내용이라 당연히 같음 |
| Playwright MCP 사용 후기 | **E2E 테스트 코드 만들기**(실제 화면에서 선택자를 읽어 지어낸 선택자 방지), 배포 확인, 실행 중에만 보이는 버그 | 우리 버그는 CSS만 읽어도 보이는 버그 |
| gstack 후기 | `/office-hours`는 **막연한 새 아이디어를 캐묻고 다시 짜는 용도**, 사용 시간 80~90%가 기획 명령. 이미 범위가 정해진 팀 과제엔 "효과가 밋밋" | 우리 기획 과제는 기능이 정해진 요청 |
| superpowers 설명·후기 | **오래 유지할 코드, 여러 작업으로 쪼개는 큰 기능**, TDD 강제. "빠른 시제품·일회성 스크립트엔 필요 없음" | 우리는 짧은 기획 1개 |
| GSD·planning-with-files 후기 | **긴 세션에서 대화가 길어질수록 품질이 떨어지는 문제(context rot)** 해결, 여러 날·여러 단계 프로젝트 | 우리 이어하기 시험은 작아서 대화가 길어지지 않음 |

## 3. 우리 시험의 문제 5가지
1. **과제가 너무 쉬움:** 정답 3개짜리 작은 코드 → 모두 만점이라 차이를 잴 수 없음.
2. **도구가 맡는 상황이 아님:** trailofbits는 "처음 찾기"가 아니라 "비슷한 것 더 찾기", security-review는 "자동 PR 검사"가 본업.
3. **설치만 하고 안 씀:** trailofbits 스킬 0회 사용. "설치됨"과 "제대로 씀"을 따로 재야 함.
4. **한 번에 끝나는 일만 봄:** 긴 작업·여러 세션·반복 실행에서 생기는 차이를 안 봄.
5. **'찾았나'만 셈:** 결과물(규칙 파일, 테스트 코드, 재현 근거) 같은 남는 것을 안 봄.

## 4. 다시 하는 시험 (도구가 맡는 상황으로)
공통 규칙: 깨끗한 환경, 정해 둔 명령만 허용, 각 3번, 정해진 규칙 채점, 도구를 **이름으로 부른 조건**과 **그냥 설치만 한 조건**을 나눔.

| # | 도구 | 새 상황 | 재는 것 |
|---|---|---|---|
| R1 | trailofbits variant-analysis | 중간 크기 코드(파일 15~20개)에 같은 원인의 SQL 주입 **8곳**을 숨기고, 1곳만 알려 주며 "비슷한 거 더 있어?" | 8곳 중 몇 곳 찾았나, 헛경보, 재사용할 Semgrep 규칙이 나왔고 실제로 돌아가나 |
| R2 | 보안 검사 전체 | 위 코드에서 **처음부터** 찾기(숨김 8곳 + 다른 종류 4곳) | 기본 vs trailofbits(audit-context-building 이름 호출) — 큰 코드에서 놓침 차이 |
| R3 | playwright / chrome-devtools | ① 실행 중에만 생기는 버그(두 번째 클릭부터 실패, 서버 응답 순서 문제) ② "이 화면의 E2E 테스트 만들어 줘" | 원인 맞힘, 만든 테스트가 **실제로 통과·실패를 맞게 하나**(선택자 지어냄 여부) |
| R4 | gstack `/office-hours`, superpowers | **막연한 새 아이디어**("동아리 회비 앱 만들고 싶어")와 **여러 날 걸릴 큰 기능** | 숨은 위험·빠진 요구를 몇 개 짚었나(정답 목록), 계획을 따라 구현했을 때 테스트 통과율 |
| R5 | GSD / planning-with-files | **긴 작업:** 작업 10단계짜리를 대화 압축(/compact)이 일어날 만큼 길게 | 뒤쪽 단계에서 앞에서 정한 규칙을 지키나(규칙 위반 수), 최종 테스트 통과율 |
| R6 | claude-code-security-review | GitHub Action 쪽은 API 키·저장소 설정이 필요 → **"시험 못 함"**으로 표시하고, 로컬 명령 결과만 "기본과 같음"으로 기록 | — |

## 5. 추천을 어떻게 쓰나 (바뀌는 점)
- "쓸 이유 없음"이 아니라 **"이 상황에선 기본으로 충분 / 이 상황에선 도구가 나음"** 두 줄로 쓴다.
- 예: "보안: 처음 훑어보기는 기본 `/security-review`. 버그 하나 찾은 뒤 같은 종류를 전부 찾을 때는 trailofbits variant-analysis(시험 결과 R1)."
- 지금 결과(시험 3·4)는 버리지 않고 **"기본으로 충분한 상황"의 근거**로 쓴다.

## 6. 토큰·시간 예상
- R1~R5 각 조건 3번 → 대략 60~80회 실행. 큰 코드·긴 작업이라 지난번보다 회당 2~5배.
- 사용량 한도에 걸릴 수 있어 **R1 → R3 → R5 → R4 → R2** 순(차이가 날 가능성이 큰 순)으로 나눠 돌린다.
- R1은 semgrep 설치(pip, 내려받기)가 있으면 "규칙이 실제로 돌아가나"까지 잴 수 있음 — 설치는 허락 뒤.
