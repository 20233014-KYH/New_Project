### 현재 상태
- `todo.py`의 `main()`에서 `delete` 명령이 바로 `delete(items, idx)` → `save()`를 실행합니다(40~41행).
- `delete()` 함수는 순수 함수라서 `test_todo.py`가 직접 호출해 테스트합니다. 이 함수에는 입력 로직을 넣지 않는 게 좋습니다.

### 설계 방침
1. **확인 로직은 `main()` 쪽에 둡니다.** `delete()`는 그대로 두어 기존 테스트 `test_delete`가 깨지지 않게 합니다.
2. **확인 함수를 따로 만듭니다.** `confirm(prompt, input_fn=input) -> bool` 형태입니다.
   - `y`/`Y`만 True, 그 외(`n`, 빈 입력 등)는 False입니다. 기본값은 "취소"로 안전하게 둡니다.
   - `input_fn`을 인자로 받으면 테스트에서 입력을 흉내 낼 수 있습니다.
3. **삭제 흐름**
   1. 번호가 범위 안인지 먼저 확인합니다. 지금은 범위 밖 번호나 숫자가 아닌 입력이면 `IndexError`/`ValueError`가 그대로 납니다. 확인을 묻기 전에 "그런 번호가 없어요"를 출력하고 종료하는 게 자연스럽습니다.
   2. 어떤 항목인지 보여 줍니다. 예: `정말 삭제할까요? (y/n)` 앞에 `3. 장보기`를 출력합니다.
   3. `y`면 삭제하고 저장합니다. 아니면 "취소했어요"를 출력하고 저장하지 않습니다.

# 삭제 확인 프롬프트 개발 계획

코드는 아직 쓰지 않았고, 파일 4개(`todo.py`, `storage.py`, `test_todo.py`, `README.md`)만 읽었습니다.

## 설계 결정
1. **확인 위치**: `main()`의 delete 분기에 둡니다. `delete()`는 건드리지 않습니다.
2. **프롬프트 문구**: `정말 삭제할까요? (y/n)`. 어떤 항목이 지워지는지 알 수 있도록 제목을 함께 보여줄지 정해야 합니다. 제 추천은 `'장보기' 정말 삭제할까요? (y/n)`입니다.

- **스크립트 자동화**: 기존 스크립트가 `delete`를 호출한다면 깨질 수 있습니다. `--yes`/`-y` 플래그로 확인을 건너뛰는 옵션을 두는 방안이 있습니다. 필요 여부는 사용자가 정해 주세요.

# 동아리 회원 관리 웹 서비스 개발 계획

## 1. 전제 (가정, 틀리면 알려 주세요)
- 규모는 회원 수십~수백 명이고, 관리자는 소수입니다.
- 회비는 **온라인 결제가 아니라 계좌이체를 관리자가 수동으로 기록**합니다. PG 연동은 범위에서 뺍니다.
- 한국어 UI 하나만 만들고, 배포는 무료 또는 저가 호스팅에 합니다.

## 2. 기술 스택 추천
| 영역 | 추천 | 이유 |
|---|---|---|
| 프레임워크 | **Next.js (TypeScript)** 풀스택 | 프론트와 API를 한 저장소에서 관리할 수 있어 소규모에 적합합니다. |
| DB | **PostgreSQL** (Supabase 또는 Neon 무료 티어) | 회원-납부 관계형 데이터에 잘 맞습니다. |
| ORM | Prisma | 스키마와 마이그레이션 관리가 쉽습니다. |
| 인증 | Auth.js, 이메일+비밀번호(argon2/bcrypt) | 세션 쿠키 방식으로 직접 구현하는 것보다 안전합니다. |
| 배포 | Vercel + 관리형 DB | 운영 부담이 적습니다. |
| 테스트 | Vitest + Playwright(핵심 흐름만) | |

익숙한 스택이 따로 있으면 그쪽으로 바꿔도 계획은 그대로 적용됩니다.

## 3. 핵심 데이터 모델
- **User**: id, 이메일(unique), 비밀번호 해시, 이름, 학번, 연락처, 역할(`member`/`admin`), 상태(`pending`/`active`/`inactive`), 가입일
- **Term(학기/회기)**: id, 이름(예: 2026-2), 회비 금액, 납부 기한
- **Payment**: id, user_id, term_id, 금액, 납부일, 방법, 메모, 기록한 관리자 id, 생성/수정 시각
- **AuditLog**: 관리자 작업 이력(누가, 언제, 무엇을 바꿨는지)

회비 납부 여부는 별도 상태로 저장하지 않습니다. 해당 학기 Payment 합계와 회비 금액을 비교해 계산하면 데이터가 어긋나지 않습니다. 결제 기록은 삭제하지 않고 취소 처리(soft delete)합니다.

## 4. 기능 범위
**회원**
- 회원가입, 로그인/로그아웃, 비밀번호 재설정
- 내 정보 수정
- 내 납부 내역과 미납 여부 조회

**관리자**
- 가입 승인/거절 (동아리 외부인 차단)
- 회원 목록: 검색, 필터(미납/활동중), 상세 보기, 상태 변경
- 학기 생성과 회비 설정
- 납부 기록 입력/수정/취소, 일괄 입력
- 학기별 납부 현황 대시보드(납부율, 미납자 목록)
- 엑셀(CSV) 내보내기
- 관리자 권한 부여/회수

**나중에 할 것 (v2)**: 미납자 안내 메일, 공지사항, 출석 관리, 계좌 입금 내역 자동 매칭

## 5. 개발 단계
| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 0. 기획 확정 | 위 가정 확인, 화면 목록과 와이어프레임 스케치 | 화면 8~10개 목록 확정 |
| 1. 기반 세팅 | 저장소, 린트/포맷, DB 연결, 스키마, 환경변수 분리, CI | 빈 앱이 배포 환경에 올라감 |
| 2. 인증 | 가입/로그인/로그아웃, 역할 기반 접근 제어(미들웨어), 비밀번호 재설정 | 회원이 관리자 URL에 접근하면 차단됨 |
| 3. 회원 기능 | 내 정보, 내 납부 내역 | 회원이 본인 데이터만 볼 수 있음 |
| 4. 관리자: 회원 관리 | 가입 승인, 목록/검색/상세, 상태 변경 | 승인 전에는 로그인 후 기능 제한 |
| 5. 관리자: 회비 | 학기 설정, 납부 기록 CRUD, 미납 현황, CSV | 실제 한 학기 데이터를 입력해 검증 |
| 6. 마감 | 감사 로그, 오류 페이지, 모바일 반응형, 접근성 점검, 보안 점검 | 체크리스트 통과 |
| 7. 배포·운영 | 첫 관리자 시딩, 백업 설정, 운영 문서, 소수 회원 시범 사용 | 실사용 시작 |

우선순위는 2→5단계가 핵심(MVP)입니다. 이 구간만 끝나도 엑셀을 대체할 수 있습니다.

## 6. 보안·개인정보 체크리스트
- 비밀번호는 해시로만 저장하고, 로그인 시도 횟수를 제한합니다.
- 권한 검사는 화면이 아니라 **서버 API마다** 합니다. 회원 A가 B의 데이터를 조회하는 경우(IDOR)를 테스트에 포함합니다.
- CSRF와 XSS 방어, 입력 검증(zod 등)을 적용합니다.
- 학번·연락처 등 개인정보는 최소한만 수집합니다. 개인정보 처리 안내 문구와 탈퇴 시 처리 방침을 정합니다.
- DB 자동 백업을 켜고, 비밀 값은 저장소에 커밋하지 않습니다.

## 7. 테스트 전략
- 단위 테스트: 납부 여부 계산, 권한 판정 로직
- 통합 테스트: API별 권한 매트릭스(비로그인/회원/관리자)
- E2E: 가입→승인→납부 기록→회원이 내역 확인

## 8. 위험 요소
- **관리자 인수인계**: 회장이 바뀔 때 권한을 이전하는 절차가 필요합니다. 4단계에 포함합니다.
- **회비 정책 변동**(분납, 면제, 환불): 모델에 `면제`와 `취소`를 처음부터 넣어 두면 나중에 비용이 덜 듭니다.
- **범위 확장**: 위 MVP 범위를 넘는 요구는 v2로 미룹니다.

2. 가입은 자유 가입 후 관리자 승인 방식으로 해도 되나요?

# 최종 개발 계획: 동아리 회원 관리 서비스

## 1. 확정 조건
- **팀**: 3명, **기간**: 6주
- **스택**: Spring Boot(Java 17+, Gradle) + MySQL 8 + React(TypeScript, Vite)
- **규모**: 회원 약 50명, 관리자 소수
- **미정이던 항목은 아래처럼 정했습니다. 바꾸려면 말씀해 주세요.**
  - 회비 납부는 온라인 결제 없이 **관리자가 계좌이체를 확인해 수동으로 기록**합니다.
  - 가입은 자유 가입 후 **관리자 승인**을 받습니다.
  - 회비는 **학기 단위**입니다. 분납은 한 학기에 납부 기록을 여러 건 허용하는 방식으로 처리합니다.

## 2. 아키텍처
- **백엔드**: Spring Boot, Spring Security, Spring Data JPA, Flyway(DB 마이그레이션), Validation
- **인증**: 세션 쿠키 방식(HttpOnly, SameSite) + BCrypt. 50명 규모에는 JWT보다 세션이 단순하고 안전합니다.
- **프론트**: React + React Router + TanStack Query + 폼 검증(react-hook-form + zod), UI는 MUI 또는 Ant Design 중 하나
- **API**: REST + OpenAPI(springdoc). 프론트와 백엔드가 이 명세를 기준으로 병렬 개발합니다.
- **배포**: 단일 VPS 또는 클라우드 VM 한 대에 Docker Compose(Spring, MySQL, Nginx가 React 정적 파일과 리버스 프록시 담당). HTTPS는 Let's Encrypt, DB는 일일 `mysqldump` 백업을 합니다.
- **CI**: GitHub Actions에서 빌드, 테스트, 린트를 돌립니다.

## 3. 데이터 모델
- **member**: id, email(unique), password_hash, name, student_no, phone, role(`MEMBER`/`ADMIN`), status(`PENDING`/`ACTIVE`/`INACTIVE`), created_at
- **term**: id, name(예: 2026-2), fee_amount, due_date
- **payment**: id, member_id, term_id, amount, paid_at, method, memo, status(`VALID`/`CANCELED`), recorded_by, created_at
- **audit_log**: id, actor_id, action, target_type, target_id, detail, created_at
- **password_reset_token**: member_id, token_hash, expires_at

납부 여부는 저장하지 않고 `VALID` 납부 합계와 `fee_amount`를 비교해 계산합니다. 납부 기록은 삭제하지 않고 `CANCELED`로 바꿉니다. 회비 면제는 금액 0원짜리 납부 기록에 메모를 남겨 처리합니다.

## 4. 역할 분담
| 역할 | 담당 | 주요 책임 |
|---|---|---|
| A (백엔드 리드) | 인증/보안, 회원 API, 인프라 | Security 설정, 권한, 배포, CI |
| B (백엔드) | 학기·납부 API, 통계, CSV, 감사 로그 | 도메인 로직, 테스트 |
| C (프론트) | React 전체 | 화면, API 연동, 반응형 |

B는 3~4주차에 여유가 생기면 프론트 관리자 화면 일부를 같이 맡습니다. 이 구간이 병목이 될 가능성이 가장 큽니다.

## 5. 6주 일정
| 주차 | 목표 | 산출물 / 완료 기준 |
|---|---|---|
| **1주** | 기반 구축 | 저장소 2개(또는 모노레포), CI, Docker Compose 개발환경, Flyway 초기 스키마, OpenAPI 초안, 화면 목록·와이어프레임 확정. **"로그인 화면이 DB까지 연결되어 뜬다"** |
| **2주** | 인증 | 가입, 로그인/로그아웃, 역할별 접근 제어, 비밀번호 재설정, 프론트 라우트 가드, 첫 관리자 시딩. 회원이 관리자 API 호출 시 403이 나옴 |
| **3주** | 회원 관리 | 관리자: 가입 승인/거절, 회원 목록·검색·필터·상세, 상태 변경, 관리자 권한 부여/회수. 회원: 내 정보 수정 |
| **4주** | 회비 핵심 | 학기 CRUD, 납부 기록 입력/수정/취소(분납 포함), 회원의 내 납부 내역·미납 표시. **여기까지가 MVP이며, 4주차 말에 내부 데모를 합니다** |
| **5주** | 현황·마감 기능 | 학기별 납부율·미납자 대시보드, CSV 내보내기, 감사 로그 조회, 일괄 납부 입력(선택), 오류 처리·빈 상태·로딩 UI, 모바일 반응형 |
| **6주** | 안정화·배포 | 보안 점검, E2E 테스트, 운영 배포, 백업 검증, 실제 데이터 이관, 운영 문서와 사용자 안내, 시범 사용 피드백 반영 |

**버퍼 규칙**: 4주차 말 MVP가 완성되지 않으면 5주차의 일괄 입력과 감사 로그 조회 화면을 먼저 뺍니다. 이 기능들 없이도 서비스는 쓸 수 있습니다.

## 6. 주요 API 범위
- `/auth`: 가입, 로그인, 로그아웃, 내 세션 조회, 비밀번호 재설정 요청/확정
- `/me`: 내 정보 조회/수정, 내 납부 내역
- `/admin/members`: 목록/검색, 상세, 승인/거절, 상태·역할 변경
- `/admin/terms`: 학기 CRUD
- `/admin/payments`: 기록/수정/취소, 학기별 조회
- `/admin/stats`: 학기별 납부 현황
- `/admin/exports`: CSV
- `/admin/audit-logs`: 조회

## 7. 화면 목록 (약 10개)
회원용: 로그인, 가입, 비밀번호 재설정, 내 정보, 내 납부 내역
관리자용: 회원 목록, 회원 상세, 가입 승인 대기, 학기 관리, 납부 관리, 납부 현황 대시보드(감사 로그는 5주차 선택)

## 8. 보안·개인정보 체크리스트
- 비밀번호 BCrypt 해시, 로그인 시도 제한, 비밀번호 재설정 토큰은 해시 저장 후 만료 처리
- 권한 검사는 **서버(`@PreAuthorize` 또는 URL 규칙) 기준**으로 합니다. 회원 A가 B의 `/me` 외 데이터를 조회하는 경우를 통합 테스트에 포함합니다.
- CSRF 토큰 적용, CORS는 같은 도메인으로 운영해 불필요하게 열지 않습니다.
- 입력 검증은 서버 Bean Validation이 기준이고, 프론트 검증은 UX 용도입니다.
- 수집 항목은 이름, 학번, 연락처, 이메일로 최소화하고, 개인정보 수집·이용 동의 문구를 가입 화면에 넣습니다. 탈퇴 시에는 개인정보를 익명화하되 납부 기록은 보존합니다.
- 비밀 값(DB 비밀번호 등)은 환경변수로 분리하고 저장소에 커밋하지 않습니다.

## 9. 테스트 전략
- **백엔드**: 서비스 단위 테스트(납부 여부 계산, 분납 합산), MockMvc 또는 Testcontainers(MySQL) 통합 테스트로 권한 매트릭스(비로그인/회원/관리자) 검증
- **프론트**: 핵심 폼과 라우트 가드 위주의 최소 테스트
- **E2E**(Playwright, 5~6주차): 가입→승인→납부 기록→회원이 내역 확인
- 모든 PR은 CI 통과와 리뷰어 1명 승인 후 병합합니다.

## 기존 데이터 호환 규칙

이 부분은 모든 단계에서 지켜야 합니다.

- 기존 `todo.json`의 `{"title", "done"}` 항목을 열어도 오류가 나지 않아야 합니다.
- 태그를 읽는 코드는 직접 `it["tags"]`로 접근하지 않고 한 곳의 헬퍼(`get_tags(it)`)만 거치게 합니다.
- `storage.py`는 수정하지 않습니다. JSON을 그대로 읽고 쓰기 때문입니다.
- 태그를 건드리지 않은 기존 항목을 저장할 때 `tags: []`를 강제로 채우지 않습니다. 사용자의 데이터를 불필요하게 바꾸지 않기 위해서입니다.

## 구현 단계

**1단계: 데이터 모델 (`todo.py`)**
- `normalize_tags(tags)`와 `get_tags(item)`을 추가합니다.
- `add(items, title, tags=None)`: 기존 호출 `add(items, "a")`은 그대로 동작합니다. 태그가 비어 있으면 키를 만들지 않습니다.
- `tag(items, idx, name)`와 `untag(items, idx, name)`을 추가합니다. 없는 태그를 제거하거나 이미 있는 태그를 추가하는 경우는 오류 없이 무시합니다.
- `storage.py`는 docstring의 형식 설명만 갱신합니다.

**2단계: 표시와 필터**
- `filter_by_tags(items, tags)`는 `(원래 번호, 항목)` 쌍을 돌려줍니다.
- `render()`는 태그가 있는 항목에만 `1. [ ] 장보기  #집 #급함`처럼 덧붙입니다.
- 필터 결과가 없을 때는 `(해당 태그의 할 일 없음)`을 보여 주어 `(할 일 없음)`과 구분합니다.
- `tags` 명령은 `집 (3)`, `급함 (1)`처럼 태그별 개수를 보여 줍니다.

**3단계: CLI 파싱 (`main()`)**
- `argparse` 서브커맨드로 정리합니다: `add`, `list`, `done`, `delete`, `tag`, `untag`, `tags`.
- 인자 없이 실행하면 지금처럼 `list`로 동작합니다.
- `add`의 제목은 여러 단어를 공백으로 받는 현재 동작을 유지합니다.
- 범위를 벗어난 번호는 트레이스백 대신 안내 메시지와 종료 코드 1로 처리합니다.

| 태그 입력 | `add "제목" -t 집 -t 급함` (반복 옵션) |
| 정규화 | 앞뒤 공백 제거, 소문자화, 중복 제거, 빈 태그 무시 |
| 필터 | `list --tag 집 --tag 급함` → AND(모든 태그를 가진 항목) |
| 기존 항목 수정 | `tag <번호> <태그…>`, `untag <번호> <태그…>` 포함 |
| 번호 | 필터해도 전체 목록 기준 번호를 유지합니다. 그래야 `done`/`delete`가 엉뚱한 항목을 건드리지 않습니다. |

## 작업 단계 (테스트 먼저)

1. **호환 테스트 먼저**: `tags` 없는 항목을 `render`/필터/`tag`에 넣어도 깨지지 않는 테스트를 가장 먼저 씁니다. 기존 테스트 4개는 수정 없이 통과해야 합니다.
2. **`todo.py`**: 태그 정규화 함수를 추가하고, `add(items, title, tags=None)`로 기본값을 빈 목록으로 둡니다. 태그가 없는 항목의 `render` 출력은 현재와 한 글자도 다르지 않아야 합니다.
3. **붙이기·떼기**: `tag`/`untag` 함수와 명령을 추가합니다. 새 명령은 번호 범위를 검사해 오류 메시지를 냅니다. 기존 `done`/`delete`는 이번에 건드리지 않습니다.
4. **보기·필터**: 태그가 있으면 `1. [ ] 장보기  #집 #급함`처럼 표시합니다. `render`에 `tags` 필터 인자를 추가해 번호는 전체 기준으로 유지합니다. 일치하는 항목이 없으면 `(할 일 없음)`을 출력합니다.
5. **CLI 파싱**: `main()`에서 `-t`와 `--tag`를 파싱합니다. 파싱이 복잡해지면 `argparse`로 바꿉니다.
6. **`storage.py`**: 형식 설명 주석만 갱신하고 동작은 바꾸지 않습니다.
7. **문서**: `README.md`에 사용법을 추가합니다.

- 정규화: 대소문자, 공백, 중복, 빈 태그
- **`tags` 없는 옛 항목**: 렌더링, 필터(결과 없음), `tag` 추가가 모두 정상 동작하는지
- 단일 태그 필터와 다중 태그 AND 필터
