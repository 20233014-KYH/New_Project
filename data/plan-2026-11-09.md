## 기준별 방법

- **기능**: README·공식 문서에서 무엇을 하는지와 주요 기능. 스킬·명령·훅·MCP 이름과 개수는 `features.json`에 이미 있으니 다시 세지 않습니다.
- **특징(다른 점)**: 같은 그룹·분야의 도구를 나란히 놓고 #13 축 값을 비교합니다. "좋다·뛰어나다"는 쓰지 않고 관찰할 수 있는 차이만 씁니다.
  - 예: caveman과 rtk는 둘 다 토큰을 줄이지만, caveman은 Claude가 **쓰는 답변**을, rtk는 Claude가 **읽는 명령 결과**를 줄입니다.
  - 토큰이 더 들어도 낫다는 말은 근거가 `tested`일 때만 씁니다. 제작자 주장은 "제작자 주장"이라고 적습니다.
- **비용**: 라이선스, 추가로 필요한 서비스·키·계정, 처음 읽는 양(팀 실측). 실측값은 첫 응답 기준이라 **작업 중 비용**(쓸 때마다 도는 훅, MCP 호출 결과)은 들어 있지 않습니다. 첫 응답 때 읽힌 MCP 도구 목록은 들어 있습니다.
- **보안성**: `data/security/scanner/`(PR #12)를 새 도구에도 돌려 접근 범위 6칸(내 파일 / 설정 바꾸기 / 명령 실행 / 밖으로 보내기 / DB·외부 서비스 / 브라우저)을 채웁니다. 분야 5의 축3에 그대로 들어갑니다. "안전하다/위험하다"는 쓰지 않고, "찾지 못함"은 "없음"이 아닙니다.
- **깊이**: README와 코드 읽기가 기본입니다. 직접 켜서 확인(`tested`)하는 건 그 차이가 추천을 가르는 경우에만 합니다. 예: "코드만 찾나, 문서도 찾나".
- 먼저 볼 자료(다시 조사하지 않음): `features.json`, 90쌍과 기본 기능 25쌍의 판정 이유 칸, `side_effects.md`, 접근 범위 표.
